# 设计说明

## 定位

Elfofera API 是一份当前可发布的 EOE 时间线、作品和录播资料库。仓库维护当前确认结果和运行代码，不维护整理过程本身。

工具链持续跟随当前版本，接口与调用方一起重构，不保留历史兼容层。错误在实际故障边界暴露，不用猜测值、统一重试或 fallback 掩盖失败。

## 数据来源与边界

事件、计划、表演、作品和录播来自官方文字、公开目录、成员及组合账号、主要录播来源和多来源曲目资料。旧站和工作簿只能作为对照线索，不能替代当前证据。

发布数据保留来源类型、URL、BV 号、日期和必要定位文字。原始图片、批量响应、代理报告、人工校对记录和失败请求保存在本机 `.local/calendar-backup-*/`，不进入仓库或运行时。

确认数据是可发布子集，不承诺历史演出或歌曲逐曲零遗漏。录播每场保留一个主要可用版本；歌曲优先收录明确切片、合集分 P 和多来源清单，不逐条观看长录播枚举。

更新窗口优先采用用户指定日期；未指定时，从本地已确认的最新事件日期向前重叠七天，检查至采集当天，并收录已发布的后续预告。本地检查记录另存采集时间与覆盖日期；本轮最新事件日期不代表此前所有内容已齐全。

核对与采纳按以下顺序执行：

1. 动态按实际发布时间筛选，忽略置顶旧帖造成的位置干扰；分页读到窗口起点。涉及窗口内安排的更早周表和公告也要检查。
2. 读取相关动态详情和直播预约字段，官方文字与可用周表原图共同核对。动态列表没有正文，不等于详情没有文字或预约标题。

   官方可能在同一条动态中替换周表图片。每次重新读取当前图片，核对图源 URL 和具体安排，不能只按动态 ID 判断没有更新。原计划保存在变更记录中，当前计划采用更新后的安排；没有明确说明时不推断修改原因或精确修改时刻。
3. 对照成员与官方回放目录，用完整投稿详情确认拟采用的日期、账号、标题和分 P；计划时间与回放标题小时分别保存，不据此推断精确实际开播时刻。
4. 计划、变更公告、实际事件分别保留并关联；预约显示“已结束”或直播间处于轮播状态，不能单独证明当天直播发生。作品投稿日期也不能直接作为直播演唱日期。
5. 当天预定场次仍缺回放时，交付前再检查一次对应成员回放目录，避免漏掉采集期间刚上传的视频。仍未取得实际发生证据的场次保留为计划，报告本次检查时间和缺口，不自动等待或循环轮询。
6. 按事件身份、BV 和动态 ID 去重，更新确认数据与当前发布快照；重新生成前端数据，导入本地开发数据库并验证受影响日期的事件、计划、回放和变更关联。生产更新仍遵循部署流程。

原始响应、图片、检查范围与未解决线索保存在本机 `.local/`；仓库只写最终确认资料和最小来源摘要。采集沿用项目的请求超时、间隔、批次上限与失败停止规则，不将“尚未读取”写成“没有新增”。

## 数据关联

- 红露早、路翼（路翼Astra）和卡门（Karmen）是露早扮演的角色，成员归属统一为 `luzao`。角色不作为独立成员或嘉宾；标题、原始署名和来源摘要保留角色名称。多个角色同场演出不增加成员人数；同场同作品同形式的不同切片合并为一次表演，保留各视频与证据。卡门也可能是作品名，只在明确表演署名或角色语境下采用这条身份关系。
- 事件表示直播、活动、发布、公告或计划。
- 计划和实际事件分开保存，取消和改期通过关联表达。
- 表演通过 `eventId` 和 `workId` 关联，不因剪辑、分 P 或跨日重复计数。
- 关联场次时核对切片明确给出的演出日期、成员、节目标题及回放；同日多场用标题、形态和投稿先后进一步区分。切片发布时间只用于检查矛盾，不直接当作演出日期。标题有差异时保留成员回放及其他录播的原题，不能仅因名称变化另建场次。线下演出和企划舞台关联对应活动，不并入同日普通直播；已证实直播发生的生日会使用直播事件及庆典分类。
- 同作品、同成员、同场次只是重复候选；合集明确区分普通演唱与弹唱、返场或再次演唱时，保留独立表演及分 P 定位。
- 作品使用稳定 ID；同名不同作品不合并。
- 录播使用 BV 作为视频身份，来源账号不等于完整参与者名单。
- 同类直播可通过可选 `series` 关联；系列是展示和筛选维度，不替代事件标题或 `contentType`。

## 直播分类与标题

直播事件使用 `contentType` 表示节目内容：`talk`（杂谈）、`singing`（歌回）、
`dance`（舞蹈）、`radio`（电台）、`game`（游戏）、`lesson`（课程或练习）、
`celebration`（生日、周年或节日）、`special`（首播等特别节目）、`mixed`（明确混合内容）
和 `unknown`（未确定）。生日与特别节目优先表达场合，电台保留节目形式；
不根据少量歌曲切片把整场直播判成歌回。

`dimension` 独立表示画面形态：`1d`、`2d`、`3d` 或 `unknown`。
明确电台且没有其他形态说明时采用 `1d`；冲突或不明确时保留 `unknown`。
明确存在形态切换时，事件使用主要录播的形态，`stages` 按顺序保留阶段标题、形态、
录播标题小时和 BV。短暂失败后重开、连续上下场改名或 2D 转电台不增加事件；
相隔较久且没有续播证据的记录分别保留，不能只凭同日同名合并。
`isUnannounced` 表示明确标注突击的直播；`false` 仅表示未发现突击标注，不证明提前预约。
这三个字段只用于直播事件，导入时随事件保存在 `data` 中。

`title` 保留实际节目标题，移除独立的回放、形态、突击标签和录播日期时间后缀。
有内容意义的主题文字、专有节目名和标点保留；清理后没有标题内容时暂保留原文字。
录播视频的 `title` 仍保留投稿名称。分类依据明确线索，不能确定的字段不从标题语气猜测，
原始事件文件备份保存在本机 `.local/`。

## 前端展示基线

直播档案前端遵循 [EOE LIVE INDEX 设计规范](live-index.md)。前端只消费确认数据，不读取本地 evidence。

## 第一版边界

数据库覆盖确认目录中的 2022-07 至 2026-10 数据，导入脚本同步写入事件、作品、表演、录播、日程计划和日程变更。API 提供只读查询，不实现自动采集和定时任务。生产部署及 AstrBot 查询插件由 infra fleet 管理，插件复用本项目的查询规则。

## 本地资料备份

`.local/calendar-backup-*/` 是研究资料的本地备份目录，包含 evidence、候选、来源快照和 reviews。它不是仓库接口，也不是发布构建输入；需要修订数据时，在本地查证后只提交最终确认结果及最小来源摘要。
